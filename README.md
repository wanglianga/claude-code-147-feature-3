# 云溪山居 · 乡村民宿旺季运营平台

面向乡村民宿旺季（节假日）的一体化运营平台：统一 **官网 / 小程序 / OTA / 电话** 四渠道的房态、价格、入住人数、宠物规则、儿童加床、早餐份数、押金与发票要求；把 **订单 → 保洁 → 布草 → 维修 → 早餐 → 事件 → 差评归因与补救 → 结算** 放进同一条住宿链路；差评复盘页把 **早餐备餐、除湿设备、保洁完成时间、布草延迟、管家沟通记录** 聚合到同一页供归因核实，店主可选择 **退款 / 补偿券 / 电话道歉 / 不予补偿**，平台持续观察客人是否修改差评，并把补偿成本计入该渠道 **真实获客成本（CAC）**；旺季结束后按渠道/房型/服务环节复盘利润，结合补救接受率给出 **渠道评分恢复、下次旺季排班与可售房量** 建议。

## 技术栈

- 前端：React 18 + Vite + Ant Design 5 + ECharts
- 后端：NestJS 10 + TypeORM（含 Swagger 文档 `/api/docs`）
- 数据库：PostgreSQL（开发用 15 验证，Compose 用 16）

## 一键启动（Docker Compose）

```bash
docker compose up --build
```

- 前端：http://localhost:8080
- 后端 API：http://localhost:3000/api （Swagger 文档：http://localhost:3000/api/docs）
- 首次启动自动建表并写入 **2026 国庆旺季（10-01~10-08，"今天"为 10-03）** 演示数据：12 间房、4 渠道、20 张订单、保洁/布草/维修/早餐记录、8 类履约事件、6 条评价与补救/改评记录（含吴先生"早餐少+房间潮湿+入住等待久"三维度差评完整证据链）。

## 本地开发

```bash
# 1. 数据库（任一方式）
docker compose up -d db                                  # 用 Compose 起 Postgres(5432)
# 或使用本机已有 PostgreSQL，创建 homestay 库后通过 DATABASE_URL 指向它

# 2. 后端（首次启动自动建表+种子数据）
cd server && npm install
DATABASE_URL=postgres://homestay:homestay123@localhost:5432/homestay npm run start:dev

# 3. 前端（Vite 代理 /api → localhost:3000）
cd web && npm install && npm run dev                    # http://localhost:5173
```

## 演示动线（种子数据已埋好完整故事线）

1. **经营看板**：入住率/ADR/RevPAR、渠道收入分布、履约事件分布、差评归因四象限（硬件/服务/超卖/餐食）。
2. **房态日历**：房间×日期占用与价格；下方库存表可见 10-01 庭院双床房、10-04 山景大床房两处**超卖**红色告警。
3. **订单管理**：新建订单统一校验宠物/加床/人数规则与库存（OTA 可强制下单并触发超卖事件）；订单详情抽屉含 **链路事件 / 保洁 / 评价补偿 / 结算明细** 页签。可现场操作：入住 → 临时加人（早餐费自动重算）→ 延迟退房（自动生成事件+保洁任务）。
4. **保洁与布草**：「智能排班」按下一单入住时间、脏污程度、维修冲突、布草库存自动派单；完成打扫扣减布草；送洗签收超时 2 小时自动记布草延迟事件。
5. **早餐备餐**：按在住人数与忌口自动汇总需求；确认备餐量不足即生成早餐供应不足事件。
6. **差评复盘（本题核心）**：吴先生 10-02 入住 201 房——上一单延迟退房 + 布草延迟致其 **等到 16:30 才进房**，当夜 **除湿机故障房间潮湿**，次日 **早餐短缺**。打开「差评复盘」→ 吴先生一行「复盘」：
   - **归因维度**：入住等待 / 房间潮湿 / 早餐供应 三条归因，可对照证据逐条标记「属实/不成立」；
   - **同一复盘页证据**：早餐备餐记录（10-03 需求 15 备 12）、除湿设备运行记录（湿度 83% 故障）、保洁完成时间（16:20，晚于 14:00 标准入住）、布草配送（床单延迟）、管家沟通时间线（客人 5 次催促/反馈）、链路事件；
   - **补救决策**：退款 / 补偿券（自动生券码）/ 电话道歉 / 不予补偿 四选一；退款与补偿券自动生成补偿记录计入结算；
   - **客人回应**：接受 → 差评事件关闭并进入观察期；拒绝 → 补偿作废、可再次补救（演示：电话道歉被拒后再退款）；
   - **差评修改观察**：补救完成后平台持续观察，客人改回 4 分以上观察结束（小程序渠道已有 2→4 分恢复样例）。
7. **事件与差评**：传统事件链与补偿记录（现金/退款/补偿券）仍可在此操作；差评（≤3 分）自动进入链路。
8. **结算中心**：每笔订单的房费、加床、早餐、宠物费、渠道佣金（OTA 15%）、赔付补偿、押金扣留/退还、净收入逐行列清。
9. **旺季复盘**：分渠道/分房型利润表、服务环节收入 vs 成本、问题自动归类；**渠道评分恢复**（补救接受率、客人改评数、均分变化）、**渠道真实获客成本**（佣金+补偿成本，单均/间夜 CAC）、**下次旺季排班建议**（保洁/管家/厨房，参考补救接受率与管家响应时长）；最下方给出下一轮节假日各房型**建议可售房量**，选择日期区间后「应用到下一轮节假日」即写入库存。

## 验证方式（实际执行过的验证）

本仓库交付前在 Linux + PostgreSQL 15 + Node 22 环境实际执行：

```bash
# 后端编译
cd server && npx tsc -p tsconfig.build.json

# 端到端 API 验证（74 项断言全部通过）
python3 scripts/verify.py
```

前端通过 `npm run build` 构建，并以 `vite preview` 验证页面、静态资源与 `/api` 代理连通（登录接口 201、复盘页接口数据正确）。
